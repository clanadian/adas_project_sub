## §1. 문서가 한 세대 낡은 채로 제안서까지 갔다 (2026-08-18)

### 증상

발표용 제안서(`Artyz720_96/proposal_roi_classifier.md`)에 96×96 판 성능을
**934,998 cycle / 9.35 ms / 10.7 FPS**, 자원을 **LUT 38,194 / DSP 202 / BRAM 64.5
/ Slice 12,918 / WNS +0.254 ns** 로 적었다. 근거는 `PROGRESS.md` §2-b·§2-c 였다.

**전부 틀렸다.** 값이 거짓이어서가 아니라 **37분 전 세대의 옳은 값**이어서다.

| | 문서에 적힌 값 (G=2) | **실제 (G=4)** | |
| --- | --- | --- | --- |
| conv2 @24×24 | 267,678 | **242,730** | −9.3% |
| **ROI 1개** | 934,998 / 9.35 ms | **910,050 / 9.10 ms** | |
| **FPS @10 ROI** | 10.7 | **11.0** | |
| LUT | 38,248 (71.89%) | **40,553 (76.23%)** | +2,305 |
| FF | 41,234 (38.75%) | **42,983 (40.40%)** | |
| Slice | 12,736 (95.76%) | **12,894 (96.95%)** | |
| **BRAM** | 65 (46.43%) | **41 (29.29%)** | **−24 타일** |
| DSP | 202 (91.82%) | **201 (91.36%)** | −1 |
| **WNS** | +0.172 ns | **+0.249 ns** | 개선 |

> 제안서에 적었던 `LUT 38,194 / Slice 12,918 / WNS +0.254` 는 한술 더 떠서
> **96 판도 아니고 64 판 값**이었다. §1-e 참조.

### 원인 — 소스가 문서 아래에서 움직였다

```
14:23  conv0_engine.h · maxpool_engine.h            (이후 안 바뀜)
14:27  체인 시작 — csynth · cosim · package · build
14:29~14:39  pool ×3 · conv0 cosim 로그 생성
15:01  체인 종료 → PROGRESS.md §2-b 작성 (여기서 문서가 멈춘다)
────────────────────────────────────────────────────────────
15:38  conv_engine.h / .cpp 수정
         OC_GROUP_TILES   2 → 4
         ACCUM_POSITIONS  576 → 1
15:40  tr8_csynth.log
15:43  tr8_cosim_2.log      ← conv2 267,678 → 242,730
15:46  tr8_cosim_1.log      ← conv1 412,302 (변화 없음)
15:48  tr8_package.log
15:49  vivado_bd.log
16:10  system/*_impl_arty96_v1.rpt · arty96_classifier_v1.xsa
16:11  vivado_build.log
```

`out_ch ≤ 64` 라서 **G=4 면 oc_tile 4개가 한 패스에 들어가고 accum 스필이
사라진다.** 그래서 conv2(out_ch=64)는 4패스→1패스로 줄고 BRAM 24 타일이
회수됐다. **conv1(out_ch=32)은 G=2 로도 이미 1패스**라 값이 그대로다.

**이 "conv1만 안 바뀐 것"이 결과를 신뢰한 근거다.** 무작위로 흔들렸다면
측정 오류를 의심해야 하지만, 바뀐 op와 안 바뀐 op가 설계와 정확히 맞았다.

### 왜 아무도 못 잡았나 — 기존 게이트의 사각지대

이 저장소에는 이미 `python/check_cosim_freshness.py` 가 있다. 소스가 움직였는데
cosim 증거가 그대로면 잡는 게이트다(주석 제거 후 SHA-256 비교, mtime 안 씀).

**그런데 이번 건은 그 게이트가 보는 방향의 반대였다.**

| | `check_cosim_freshness` 가 잡는 것 | **이번 건** |
| --- | --- | --- |
| 소스 | 바뀜 | 바뀜 |
| cosim 증거 | **낡음** ← 잡는다 | **갱신됨** |
| 그 숫자를 인용한 문서 | 범위 밖 | **낡음** ← 아무도 안 본다 |

즉 **증거는 멀쩡했고 문서만 낡았다.** `bash run.sh check` 는 로그에서 값을
다시 읽어 오므로 **처음부터 올바른 910,050 을 출력하고 있었다.** 게이트는
정상 동작했고, 재빌드 후 아무도 그것을 다시 읽지 않았을 뿐이다.

`hls/arty_96_classifier/python/` 에는 freshness 게이트 자체가 없다(원 저장소에만
있다). 다만 그것을 이식했어도 **이번 건은 못 잡았을 것이다** — 증거가 낡지
않았기 때문이다.

### 어떻게 확인했나 — 세 겹

값이 어긋난 것을 발견한 뒤, 어느 쪽이 맞는지를 **세 층으로** 확인했다.

1. **게이트 출력** — `bash run.sh check` → 910,050, rc=0
2. **로그 원문 환산** — `$finish called at time : 2427295 ns` ÷ 10 ns = 242,730 cycle
   (리포트가 지워져도 로그의 `$finish` 시각에서 복원 가능하다)
3. **그 실행이 옳은 형상을 돌렸는지** —
   `[conv2 (32->64 @24x24)] PASS: 36864 output values matched ... (img 24x24x32 -> 24x24x64, k=3, pad=1)`

3번이 핵심이다. **로그가 PASS라는 것과 그 로그가 내가 생각한 것을 돌렸다는 것은
다른 명제다.** 이 저장소는 같은 함정을 이미 여러 번 밟았다
(`verification-pointer-rot-log.md`).

자원·타이밍은 요약이 아니라 리포트 원문에서 읽었다 —
`system/utilization_impl_arty96_v1.rpt`, `system/timing_impl_arty96_v1.rpt`
(Clock Summary **100.000 MHz**, 실패 엔드포인트 **0 / 169,319**, WHS +0.011).

### §1-b. 여섯 개 숫자가 두 시각에서 왔는데 그게 정상이다

현재 ROI 합계 910,050 을 구성하는 6개 로그는 시각이 갈린다.

| op | 로그 시각 | 유효한가 |
| --- | --- | --- |
| pool0/1/2 | 14:29~14:31 | ✅ `maxpool_engine.h` 가 14:23 이후 안 바뀜 |
| conv0 | 14:39 | ✅ `conv0_engine.h` 가 14:23 이후 안 바뀜 |
| conv2 | 15:43 | ✅ 15:38 수정 이후 |
| conv1 | 15:46 | ✅ 〃 |

**"로그가 오래됐다"가 "값이 낡았다"는 아니다.** 판단 기준은 시각이 아니라
**그 로그를 만든 소스가 그 뒤에 바뀌었는가**다. 엔진이 3개로 분리돼 있어
conv 쪽만 재측정하면 됐고, 실제로 그렇게 했다.

### §1-c. 아직 안 고쳐진 것 — 세대가 섞인 비교표

**64·128 판은 다시 안 쟀다. 그쪽은 여전히 G=2 다.**

| 입력 | ROI cycle | FPS @10 ROI | 엔진 세대 |
| --- | --- | --- | --- |
| 64×64 | 434,544 | 23.0 | G=2 |
| **96×96** | **910,050** | **11.0** | **G=4** |
| 128×128 | 1,629,060 | 6.1 | G=2 |

세로로 비교하면 **96 이 실제보다 유리하게 보인다.** 64·128 을 G=4 로 다시
재기 전에는 이 표에서 해상도 경향을 읽으면 안 된다. 제안서 §11-1 과
`PROGRESS.md` §2-b 배너 양쪽에 경고를 달았다.

재측정 비용은 cosim 4판(conv1·conv2 × 2트리)이고 **단독 실행만 가능**하다.

### §1-d. `PROGRESS.md` 를 지우지 않고 배너를 얹었다

옛 값이 왜 그랬는지가 근거로 남아야 같은 실수를 반복하지 않는다. §2-b 머리에
G=2/G=4 대조표와 원인(`OC_GROUP_TILES` 2→4)을 넣고 본문 표는 그대로 뒀다.
저장소 규칙과 같다 — **결론이 뒤집혀도 근거는 보존한다.**

### §1-e. 딸려 나온 결함 2건 — 둘 다 "다른 판의 옳은 값"

같은 검토에서 두 개가 더 나왔다. **셋 다 유형이 같다:** 숫자가 거짓이 아니라
**출처가 다른 대상**이었다.

| 결함 | 적힌 값 | 실제 | 왜 안 보였나 |
| --- | --- | --- | --- |
| GAP/FC 연산량 | 약 4,400 MAC | **약 9,500** (12×12×64 + FC) | **64 판 값**(8×8×64)이다. 그럴듯한 크기라 검산하지 않았다 |
| §8-2 자원표 | LUT 38,194 / Slice 12,918 / WNS +0.254 | LUT 40,553 / Slice 12,894 / WNS +0.249 | **64 판 표**를 96 판 절에 넣었다. 세 판 수치가 서로 가까워서 눈으로 안 걸린다 |

`GAP` 는 **해상도에 비례하는 유일한 PS 연산**이다(나눗수 64/144/256).
해상도를 바꾸면 따라 움직이는데 상수처럼 취급됐다 —
`feedback_constant_has_coupled_code` 와 같은 유형이다.

정정하면서 **PL 대비 비율(0.04%)** 로 바꿔 적었다. 절대값은 해상도마다 다시
틀리지만 비율은 안 틀리고, 발표에서 쓸모도 더 크다.

### 교훈

1. **숫자를 인용하기 전에 "어느 세대"부터 확인한다.** 값의 진위보다 출처가
   먼저다. 이번 건은 값이 정확했고 대상이 달랐다.
2. **재빌드 뒤에는 게이트를 다시 읽는다.** `run.sh check` 는 내내 옳은 값을
   출력하고 있었다. 게이트는 실행해야 게이트다.
3. **문서 안의 숫자에는 게이트가 없다.** 증거 파일은 검사되지만, 그 값을
   손으로 옮겨 적은 문서는 아무도 안 본다 — `feedback_handwritten_lists_rot`.
4. **PASS 는 "옳은 것을 돌렸다"가 아니다.** 형상 줄까지 읽어야 한다.
5. **한 판을 고쳤으면 형제 판의 유효성이 깨졌는지 본다.** 96 을 G=4 로 올린
   순간 64·128 과의 비교표가 조용히 무효가 됐다.

### 제안 — 게이트로 만들 수 있는가

`run.sh check` 는 이미 정본 숫자를 stdout 으로 낸다. `PROGRESS.md` 와 제안서가
인용한 값이 그 출력과 일치하는지 대조하는 게이트는 원리적으로 가능하다.

다만 **문서 본문을 파싱하는 게이트는 오탐이 잦고**, 이 저장소는 문서 링크
게이트가 처음 211건의 거짓 경보를 냈던 전례가 있다. 대안은 숫자를 문서에
직접 쓰지 않고 **게이트 출력 파일 한 곳에서 생성**하는 쪽이다.

**미착수.** 착수한다면 비용과 오탐률을 먼저 재고 결정할 것.

## §2. 최적화가 cosim 에서 지고, 그 이유가 리포트에 이미 적혀 있었다 (2026-08-18)

### 증상

출력 쓰기 루프(`FINISH_WR`)를 4레인 UNROLL 로 바꿨다. 모든 사전 신호가 초록이었다.

```
csim  : CLASSIFIER CONV SUITE PASS (6 shapes)     ← 비트일치
csynth: LUT 47,543 -> 50,581 (+3,038), DSP 94 -> 100, Estimated 7.659 ns (불변)
cosim : conv1 341,657 -> 456,660                  ← +33.7% 느려짐
```

예상은 −16.2% 였다.

### 원인

같은 csynth 실행의 **서브 리포트**에 답이 있었다:

```
|- FINISH_WR | min 21 | max 49 | iteration latency 22 | achieved II 4 | target 1 | trip 1~8 |
```

반복을 32 → 8 로 줄였는데 **II 가 1 → 4** 가 되어 곱이 그대로다. 반복 지연은
12 → 22 로 늘었으니 순손실이다.

II=4 의 물리적 이유: `ofmap` 은 **m_axi 쓰기 포트가 하나**다. `UNROLL` 은
데이터패스를 복제하지만 포트를 복제하지 않으므로 바이트 저장 4개가 그 포트에서
직렬화된다. 사이클당 4바이트를 내보내려면 4바이트 **워드**여야 하는데, 그건
`conv_engine.cpp` 의 opack 주석이 주소 affine 논거로 이미 닫아 둔 방향이다.

### 조치

- W5 를 되돌리고 주석을 실측으로 교체했다. **출력 쓰기 경로는 워드 패킹·레인
  언롤 양방향이 다 실측으로 닫혔다** — 세 번째 변형을 만들지 말 것.
- 주석에 남아 있던 Zybo 추정(+3,800 LUT, "이 파트에는 과분")은 **반대 이유로
  틀렸다.** 이 트리 csynth 는 LUT +3,038 으로 감당 가능했다. **느려서 진 것이지
  커서 진 게 아니다.**

### 다음에 할 일

이 엔진에서 csynth 의 **사이클·면적 예측은 못 쓴다**(부호가 세 번 뒤집혔다).
그러나 **`achieved II` 와 II 위반 사유는 예측이 아니라 스케줄링 사실**이다.
사이클을 건드리는 변경은 LUT 칸이 아니라 II 부터 읽을 것.

## §3. II=2 의 원인을 두 번 연속 틀리게 짚었다 (2026-08-18)

### 증상

읽기 루프를 시프트 루프에 접은 뒤(W6), `FUSED_SHIFT_STEP` 의 II 가 1 → 2 로 올라
이득의 2/3 을 먹었다. 로그가 원인 배열과 소스 줄번호까지 찍어 줬다.

```
WARNING: [HLS 200-885] II Violation in 'FUSED_SHIFT_STEP': Unable to schedule
'store' (conv_engine.cpp:815) on array 'window' due to limited memory ports (II = 1).
INFO: [HLS 200-1470] Target II = 1, Final II = 2, Depth = 13
```

### 두 번의 오진

| 가설 | 조치 | 결과 |
|---|---|---|
| 뱅킹 부족 | `window` 에 `complete dim=2/3` 추가 | II **2 그대로**, **LUT 47,708 → 47,708 바이트 동일**, FF 만 +1,794 |
| 런타임 인덱스 | 꼬리 쓰기의 `k-1` 을 컴파일타임 루프 + 술어로 | II **2 그대로**, LUT +434 |

**LUT 가 한 톨도 안 움직인 것이 첫 가설을 죽인 증거였다** — 뱅킹이 병목이면
면적이 움직인다. 프라그마는 적용됐다(로그의 `Applying array_partition ...
Complete on dim 2. Complete on dim 3.`), 겨냥이 틀렸을 뿐이다.

### 실제 원인 (미해결, 의도적)

II 위반이 지목하는 store 는 꼬리가 아니라 **창 시프트 자신**
(`window[ic][ky][kx] = window[ic][ky][kx+1]`)이다. 한 뱅크가 lane 당 6개의 시프트
쓰기를 받는 **구조 자체**가 원인이고, 없애려면 창을 물리적으로 옮기지 않고
인덱스를 회전시키는 재구조화(circular window)가 필요하다. `MAC_REDUCE` 의 읽기
인덱싱까지 바꿔야 하고 **남은 이득은 conv1 위치당 4 (약 1%)** 라 착수하지 않았다.

### 다음에 할 일

프라그마를 넣고 II 가 안 바뀌면 **면적이 움직였는지 먼저 볼 것.** 안 움직였으면
그 프라그마가 겨냥한 것이 병목이 아니다 — 다른 가설을 세우기 전에 그것부터 확인.

## §4. 빌드가 `IP 저장소 없음` 으로 멈춘다 — 하루에 두 번 (2026-08-18/19)

### 증상

```
== FATAL: IP 저장소 없음: .../conv0_engine/conv0_engine_prj/solution1/impl/ip
== exit=1
```

리포트·XSA 시각이 그대로라 "빌드가 아예 안 돌았다" 로 보인다.

### 원인

`csynth` / `cosim` 의 `open_project -reset` 이 **그 엔진의 export 된 IP 를 지우고
시작한다.** 진단 cosim 을 여러 번 돌린 뒤 빌드를 걸면 반드시 이 상태가 된다.

어젯밤엔 `conv_engine_tr8`, 오늘 아침엔 `conv0_engine` 이 그렇게 사라졌다.
두 번째는 **"이번엔 pool 만 바꿨으니 pool 만 재패키징"** 이라는 손 판단이 틀려서
생겼다.

### 조치

`check_shapes.py §6` 에 **빌드 전 세 엔진 IP 존재 전수 확인**을 넣었다(빌드 tcl 의
IP 경로 목록에서 유도하므로 엔진이 늘어도 따라온다). 실제 결함 상태로 변이 시험함.

⚠️ 이 검사는 **csynth/cosim 이 도는 동안 반드시 FAIL 한다** — 사실 자체는 맞지만
(지금은 빌드할 수 없다) 이유를 메시지에 적어 두지 않으면 사람이 "원래 뜨는 것"
으로 배우고 진짜일 때도 무시하게 된다. 메시지에 그 문장을 넣어 두었다.

## §5. csim 이 통과하는데 포화 경로는 한 번도 안 돌았다 (2026-08-19)

### 증상

없다. 그게 문제였다. `csim PASS` 가 계속 나왔고 그것을 근거로 최적화 3건을
채택했다.

### 발견

golden 출력의 값 분포를 직접 열어 봤다.

```
out_conv0_96x96x16  고유값 16개  범위 -2..13   포화 0.0%
out_conv1_48x48x32  고유값 19개  범위 -2..16   포화 0.0%
out_conv2_24x24x64  고유값 15개  범위 -8..6    포화 0.0%
```

int8 의 256 값 중 **15~19개(약 6%)** 만 밟고 ±127/−128 을 **한 번도** 밟지 않는다.
스탠드인 가중치가 난수라 이득이 작기 때문이다. 실제 학습 가중치는 포화한다.

### 증명

엔진의 클램프를 `127 → 126` 으로 바꾸고 csim 을 돌렸다.

```
[extra: saturation sweep 16->32 @32x32] FAIL: 6780/32768 values mismatched
나머지 6개 형상: 전부 PASS
```

**기존 6개 형상은 전부 눈을 감고 통과했다.**

### 조치

TB 에 포화 형상을 추가했다(`requant_shift=33`, 포화 20.9%). 그리고 그 형상 자체가
눈멀지 않도록 **포화율 구간(2~90%)을 TB 가 스스로 검사**한다 — 처음 `shift=24`
로 넣었을 때 **99.5%** 가 나왔고(전부 클립되면 0% 만큼 무의미) 그 검사가 걸렀다.

### 다음에 할 일

커버리지는 **통과율이 아니라 값 분포**로 확인할 것. "비트일치 PASS" 는 그 형상이
밟은 경로에 대해서만 참이다.

## §6. 인계 패키지가 PS 쪽에서 컴파일되지 않는다 (2026-08-19)

### 증상

저장소 안에서는 아무 문제가 없다. 패키지를 저장소 **밖으로 복사해서** 컴파일하면:

```
sw/classifier_run.c:58:10: fatal error: ../HW/classifier_net.h: No such file or directory
   58 | #include "../HW/classifier_net.h"
```

### 원인

`sw/arty_cls_address_map.h` 와 `sw/classifier_run.c` 가 `../HW/classifier_net.h`
를 include 하는데 **그 파일을 패키지에 안 실었다.** 저장소 안에서는 상대경로가
우연히 트리의 `HW/` 로 풀려서 아무도 몰랐다.

문서 검사·해시 검사·게이트 어느 것도 이걸 못 잡는다. **격리 복사본에서 실제로
컴파일해야만** 드러난다.

### 조치

생성기가 `HW/classifier_net.h` 를 패키지 루트의 `HW/` 에 함께 싣는다
(`sw/../HW` 가 거기로 풀린다). `xil_io.h` / `xparameters.h` 는 Xilinx BSP 가
제공하는 것이라 패키지에 없는 게 정상이다.

### 다음에 할 일

인계 전에 **패키지를 `/tmp` 로 복사해 `gcc -fsyntax-only` 를 한 번 돌릴 것.**
저장소 안에서의 성공은 자립성을 증명하지 않는다.

## §7. 게이트가 통과했는데 검사가 눈멀어 있었다 (2026-08-19, 3회)

### 증상

전부 "OK" 또는 "불일치 0건" 으로 보고됐다.

| 검사 | 실제 상태 | 단서 |
|---|---|---|
| 드라이버 오프셋 대조 | 정규식이 매크로 형식과 안 맞아 **양쪽 0개**를 셈 | "생성 0개 · 드라이버 0개 · 불일치 0건" |
| 가중치 바이트 대조 | op 테이블 정규식이 이름 필드를 빠뜨려 **conv 0개** | "conv 0개 검사 · 불일치 0" |
| 환경변수 이름 일치 | `"CONV0_DIAG_W" in tb` 가 `CONV0_DIAG_WX` 에도 참 | 변이 시험이 **통과** |

### 조치

- 세 검사 모두 **대조 건수 하한**을 함께 검사하게 했다
  (`check(_cmp >= 8, "... >=8 이어야 검사가 눈뜬 것")`). 실제로 그 하한이
  직후에 만든 다른 버그(`check()` 반환값으로 분기 → 전 엔진 `continue`)를 잡았다.
- 이름 비교는 부분 문자열 대신 **집합 비교**로 바꿨다. 양방향 변이로 확인.

### 다음에 할 일

**"0건" 을 통과로 읽지 말 것.** 0 은 "문제 없음" 과 "안 봤음" 을 구분하지 않는다.
새 검사에는 대조 건수 하한을 같이 넣을 것.

## §8. 변이 시험이 아무것도 증명하지 않았다 (2026-08-19)

### 증상

불변량 5개를 깨뜨리고 게이트를 돌렸더니 **5개 전부 `rc=1`** 이 나왔다.
"전부 잡힌다" 로 읽을 뻔했다.

### 원인

**기준선이 이미 `rc=1`** 이었다. 그 시점에 cosim 이 돌고 있어서 IP 가 지워진
상태(§4)였고, 게이트는 그것 때문에 실패하고 있었다. 변이는 아무 영향이 없었다.

같은 스윕에서 `sed` 치환이 **0건**인 변이도 두 개 있었다 — 대상 문자열이 파일에
아예 없었다. 즉 변이가 적용조차 안 된 채 "잡혔다" 로 셀 뻔했다.

### 조치

스윕 절차를 셋으로 고정했다.

1. **기준선이 `rc=0`** 임을 먼저 확인한다
2. 변이가 **실제로 적용됐는지** 치환 건수로 확인한다
3. `check_shapes` 만이 아니라 **전체 게이트**(`run.sh check`)로 판정한다

다시 돌린 결과: M1(op 테이블 채널)·M2(`PE_OC`)·M3(`WIN_SUB`) 잡힘,
M4·M5 는 대상이 **생성물**이라 게이트가 재생성하며 덮음(거짓음성 아님).

### 다음에 할 일

`rc=1` 은 "변이가 잡혔다" 가 아니라 "무언가 실패했다" 이다. **기준선이 초록일
때만 변이 결과를 읽을 것.**

## §9. 되돌리기가 무효였고 게이트가 말했는데 안 읽었다 (2026-08-19)

### 증상

manifest 의 `gap_divisor` 를 64 로 바꾸는 변이를 넣고 되돌린 뒤, 게이트가
`복원 rc=1` 을 찍었다. 그대로 다음 작업으로 넘어갔다. 나중에 확인하니
**변이가 그대로 남아 있었다.**

### 원인

`python/gen_manifest.py` 는 파일을 쓰지 않고 **stdout 으로 출력한다**
(`verif_host/build_and_run.sh` 가 `> forps_golden/manifest.json` 으로 받는다).
"복원" 으로 돌린 `python3 python/gen_manifest.py >/dev/null` 은 **아무것도 안 했다.**

### 조치

`> forps_golden/manifest.json.new` 후 `mv` 로 재생성했다. 게이트는 처음부터
정확히 이 상태를 `rc=1` 로 말하고 있었다.

### 다음에 할 일

- 이 저장소의 생성기 중 일부는 **stdout 에 쓴다.** `>/dev/null` 로 돌리면
  파일이 안 바뀐다.
- **게이트가 낸 `rc=1` 을 넘기지 말 것.** 그때 읽었으면 그 자리에서 끝났다.
