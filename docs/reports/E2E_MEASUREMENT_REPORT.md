측정 2026-08-20 ~ 2026-08-21 · 측정자 Claude
· 대상 DB 배포본(`z7_classifier_96_hls_100mhz_dsppack`, 100 MHz)

이 문서는 초기 계획의 **"엔드투엔드 FPS 측정"**을 완료한 결과다. 모든 숫자는

## 1. 측정 구성

```
USB 카메라 ─▶ Jetson Nano ─TCP:5000─▶ Arty Z7-20 ─UART:115200─▶ RPi(TurtleBot)
              YOLOv8n          9.7 ms        PL 6.6 ms            49.7 Hz
              proposal 28.2 ms              PS  7.7 ms
```

| 장비 | 역할 | 비고 |
|---|---|---|
| Jetson Nano | 카메라 캡처, ROI proposal, crop, TCP 클라이언트 | `~/start_adas.sh` |
| Arty Z7-20 | INT8 CNN 분류(PL) + 안전 판단 + UART 송신 | `ADAS_UART_PORT=/dev/ttyPS1 ADAS_TCP_NODELAY=1` |
| RPi | 안전상태 수신, `cmd_vel` 중재, **Jetson↔Arty 라우팅** | `~/start_robot.sh` |

RPi 가 두 보드 사이를 라우팅하므로 **그 구간 트래픽이 RPi 에서 전부 잡힌다.**
`tcpdump -i enx00e04c680398 'tcp port 5000'` 로 측정했다.

## 3. TCP 왕복 — 40 ms 지연과 그 제거

### 3.1 수정 전후

`jetson_roi_client` 측정 요약의 `TCP round-trip (per ROI)` 원본.

| | n | median | mean | p95 |
|---|---:|---:|---:|---:|
| 수정 전 | 4,670 | **51.608 ms** | 48.248 ms | 53.906 ms |
| 수정 후 | 4,118 | **9.706 ms** | 9.894 ms | 9.954 ms |

**5.3배.** 서버가 7.708 ms 를 쓰므로 남는 2.0 ms 가 배선·시스템콜이다.

### 3.2 원인 — 패킷으로 확인

수정 전, 한 왕복(`tcpdump -ttt`, 직전 줄로부터의 경과):

```text
 0.000000  젯슨 → 아티  length 20      요청 헤더
 0.000076  젯슨 → 아티  length 8688    이미지
 0.000337  아티 → 젯슨  ACK            즉시
 0.007805  아티 → 젯슨  length 20   ←  응답 헤더. 여기까지가 계산 전부 (7.8 ms)
 0.040777  젯슨 → 아티  ACK         ←  40 ms 공백
 0.000453  아티 → 젯슨  length 12   ←  응답 본문
```

**아티는 답을 7.8 ms 만에 만들어 놓고 40 ms 를 못 보내고 있었다.** PS 가 응답을
헤더(20 B) + 본문(12 B) **두 번에 나눠 write** 해서, 서버 쪽 Nagle 이 두 번째
작은 write 를 첫 20 B 의 ACK 이 올 때까지 붙들었고 젯슨의 delayed-ACK 가
40 ms 뒤에 왔다.

수정 후 같은 지점:

```text
 0.007804  아티 → 젯슨  length 20
 0.000195  젯슨 → 아티  ACK         ←  0.2 ms (전 40.8 ms)
 0.000395  아티 → 젯슨  length 12
```

### 3.3 프레임 시간에 미친 영향

ROI 개수별 프레임 시간(중앙값). 같은 보드·같은 비트스트림이다.

| ROI/프레임 | 수정 전 | 수정 후 | 배율 |
|---:|---:|---:|---:|
| 1 | 80.070 ms (12.5 FPS) | **38.655 ms (25.9 FPS)** | 2.1× |
| 2 | 132.198 ms (7.6 FPS) | **48.499 ms (20.6 FPS)** | 2.7× |
| 3 | 184.088 ms (5.4 FPS) | **58.262 ms (17.2 FPS)** | 3.2× |
| 4 | 239.941 ms (4.2 FPS) | — | |

수정 전에는 ROI 가 하나 늘 때마다 프레임이 **51 ms 씩** 길어졌다. 그중
43 ms 가 대기였다.

> ⚠️ **2026-08-21 현재 실보드는 아직 조치 A(`ADAS_TCP_NODELAY=1`) 상태다.**
> 저장소 소스(`arty/ps_db/src/network/tcp_roi_server.c`)에는 write 합치기가
> 반영돼 있으나, 보드 바이너리는 재빌드되지 않았다. tcpdump 로 확인하면
> 응답이 여전히 `length 20` + `length 12` 두 패킷이다(간격은 0). 환경변수를
> 빼고 띄우면 40 ms 가 그대로 돌아온다. 재배포 후 `length 32` 한 패킷을
> 확인해야 완료다. → [`PS_TCP_RESPONSE_FIX.md`](PS_TCP_RESPONSE_FIX.md)

> **정정 (2026-08-25).** 위 경고는 작성 시점 기록이며 지금은 맞지 않는다.
> 확인된 사실은 두 가지다. (1) 저장소 소스
> `arty/ps_db/src/network/tcp_roi_server.c` 의
> `adas_tcp_roi_server_send_result()` 는 헤더 20 B 와 결과 12 B 를 한 버퍼에
> 담아 `send_all()` **한 번**으로 보낸다. (2) 같은 날 16:30 세션에서 TCP 왕복
> 중앙값이 `9.706 ms → 8.236 ms` 로 줄었다
> (`SHUTDOWN_LOG_2026-08-21_1630.md` §4).
>
> **응답이 실제로 단일 TCP 세그먼트(`length 32`)로 나가는지는 확인하지
> 않았다.** tcpdump 재확인 기록이 없으므로 미확인으로 남긴다.

## 4. 엔드투엔드 — 프레임율·처리량

`jetson_roi_client` 측정 요약 원본, 2026-08-21 라이브 카메라.

| | 세션 A | 세션 B |
|---|---:|---:|
| 측정 구간 | 1,735.3 s | 2,279.3 s |
| 완료 프레임 | 44,507 | 49,315 |
| **프레임율** | **25.65 FPS** | **21.64 FPS** |
| 분류한 ROI | 47,102 | 87,918 |
| **ROI 처리량** | **27.14 ROI/s** | **38.57 ROI/s** |
| 프레임당 ROI | 1.06 | 1.78 |
| 응답 상태 | `status=0` 47,102건 | `status=0` 87,918건 |

프레임당 ROI 가 많은 세션 B 가 프레임율은 낮고 ROI 처리량은 높다 — ROI 하나에
9.7 ms 가 더 붙기 때문이다. 예측과 일치한다.

### 4.1 단계별 지연 (세션, n=2,051)

```text
  stage latency (ms)                    n    median      mean       p95       max
  capture (incl. camera wait)        2051      0.003     0.005     0.004     0.368
  proposal inference                 2051     28.229    28.434    29.253    32.537
  crop+prepare (per ROI)             4118      0.257     0.253     0.332     0.602
  TCP round-trip (per ROI)           4118      9.706     9.894     9.954   215.837
  MJPEG publish                      2051      0.249     0.264     0.297     4.519
  frame total                        2051     48.501    49.135    50.071   258.719
```

**병목은 proposal 28.2 ms 다.** 프레임당 ROI 2개 기준으로 보면:

```text
28.2 (proposal) + 2 × (0.26 crop + 9.7 왕복) + 0.25 (MJPEG) ≈ 48.4 ms
```

측정된 `frame total` 중앙값 48.501 ms 와 맞는다. **가속기를 더 빠르게 해도
지금 구성에서는 프레임율이 거의 안 오른다** — proposal 을 줄여야 한다.

### 4.2 기존 문서와의 차이

`DB_EB_VERIFICATION_SUMMARY.md` 는 end-to-end 를 **14.83 ROI/s** 로 기록하고
있다. 그 측정은 **TCP 40 ms 지연이 있던 시점**이고 ROI 1~2개/프레임 조건이었다.
지금은 같은 보드에서 **38.57 ROI/s** 다. 그 문서의 결론("Jetson 이 병목이라
DB/EB 차이가 안 드러난다")은 지금도 유효하지만, **수치는 갱신이 필요하다.**

## 5. UART 안전 프레임

### 5.1 원시 바이트 (RPi `/dev/ttyS0`, 수신 노드 정지 상태)

```text
수신 바이트 수: 447
앞 60바이트 : a5 02 57 a5 02 57 a5 02 57 a5 02 57 a5 02 57 ...
유효 프레임 : 149  / 버린 바이트: 0
프레임률    : 49.7 Hz
```

**버린 바이트 0개.** 수신 루프는 매직(`0xA5`)이 아니거나 CRC 가 틀리면
1바이트씩 버리고 다시 찾는다. 0개라는 것은 한 바이트도 어긋나지 않았다는
뜻이고, 보율·프레이밍·배선·GND 가 전부 맞아야 나온다.

| 상태 | 바이트 |
|---|---|
| CLEAR | `a5 00 59` |
| SLOW | `a5 01 5e` |
| STOP | `a5 02 57` |

### 5.2 송신원 확인 (A/B)

| Arty 서버 | RPi 수신 |
|---|---|
| 실행 중 | 447 바이트 / 3초 (49.7 Hz) |
| 정지 | **0 바이트** |

### 5.3 판단이 살아 있다는 증거

`/adas/safety_state` 의 **Publisher count 는 1**(= `uart_safety_receiver`)이고,
이 노드는 **유효 CRC 프레임이 올 때만** publish 한다. 기본값도 자체 heartbeat
도 없다. 그리고 파이프라인 상태에 따라 값이 바뀌었다.

| 조건 | 10초간 분포 |
|---|---|
| 젯슨 정지 | STOP 100 % |
| 젯슨 기동 | **CLEAR 159 / SLOW 161** |

SLOW(state=1)까지 나온 것이 결정적이다 — 고정값이 아니라 Arty 가 장면을 보고
판단한 결과가 그대로 넘어오고 있다.

## 6. 검출 0건 프레임 문제 (수정 완료)

안전 판단은 Arty 가 하는데, **PS 는 요청이 온 프레임에서만 판단을 갱신한다.**
젯슨이 ROI 0개인 프레임을 통째로 건너뛰면 갱신이 끊기고 PS 의 stale watchdog
(500 ms)이 STOP 을 낸다 — **빈 화면(=안전)인데 로봇이 멈춘다.**

20초 A/B 실측(다른 조건 동일):

| | CLEAR | STOP |
|---|---:|---:|
| heartbeat 끔 (`ADAS_EMPTY_FRAME_HEARTBEAT=0`) | 393 | **486 (55 %)** |
| heartbeat 켬 | 881 | **0** |

수정: `objectness=0` 인 heartbeat ROI 를 주입한다. `DetectionAdapter` 가
`min_objectness`(0.25) 미만을 Rejected 로 버리므로 **판단에 절대 끼지 않고**,
프레임 경계만 전달된다.

매 프레임 보내면 빈 화면에서 FPS 가 반토막나서(29.28 → 12.33) 간격
스로틀(`ADAS_HEARTBEAT_INTERVAL_MS`, 기본 150 ms)을 넣었다. 실제 ROI 요청도
같은 타이머를 갱신하므로 물체가 보이는 동안에는 heartbeat 가 나가지 않는다.

| | FPS |
|---|---:|
| heartbeat 없음 (빈 화면) | 29.28 |
| 매 프레임 heartbeat | 12.33 |
| **150 ms 스로틀** | **26.56** |
